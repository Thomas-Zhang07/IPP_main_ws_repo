## 0. 一页结论

| 问题 | 结论 |
|---|---|
| 当前能做到什么 | 4 种固定音效（C4、小星星、200 Hz、直通）+ 可转向 40 kHz 声束 |
| 提升指向性 | 主机侧算法（抽稀、抖动、相位优化、零陷、校准）**不用改 FPGA**；逐通道幅度需要固件升级；根治栅瓣需要新阵列 |

- 阵列：16×16 = 256，10 mm 间距，孔径约 0.15 m

- 主瓣：约 3°（半功率），零点到零点约 6.6°
- 栅瓣：正前方 ±59°（10 mm > λ/2）
- 相位：16 档，每档 22.5°
- 帧：258 字节（0xFE + 256 + 0xFD）
- 链路：38400 baud，8N1，约 67 ms/帧，约 15 帧/秒
- FPGA：EP4CE6E22C8，逻辑 5,621 / 6,272（90%），M9K 1 / 30，乘法器 0 / 30

## 1. 提升指向性

### 1.1 先定义"指向性"提升的是什么

| 指标 | 现状 | 算法能做什么 |
|---|---|---|
| 主瓣宽度 | 0.15 m 孔径 @ 40 kHz ≈ 3° | 基本不能；要更窄只能加大孔径/提高频率 |
| 旁瓣 | 均匀激励约 −13 dB | 能显著压，典型 −20 ~ −30 dB |
| 栅瓣 | ±59°，理想阵列因子下接近主瓣 | 能打散/压低 10 ~ 20 dB，根治要 ≤ λ/2 间距 |
| 相位误差/量化 | 16 档 = 22.5° | 校准 + 优化能改善 |

结论：**"提升指向性"主要是压旁瓣/栅瓣、填零陷、做相位校准，而不是把 3° 主瓣再变窄。** 主瓣宽度是孔径和频率的物理限制。

---

### 1.2 主机 Python 算法（不改 FPGA）

相位图案本来就是主机算好、量化成 256 个 4-bit 值再发下去的，FPGA 只负责 latch。所以以下算法都能先在 Python 里做。

#### 1.2.1 二值抽稀 / 密度加权

**原理**：不能连续调幅，但可以开关阵元。用窗函数（Hann / Gaussian / Chebyshev）算出每个阵元的"密度"，按密度选一部分开启。

```text
a_n ∈ {0, 1}
p_n = window(r_n)          # 密度
a_n = 1 以概率 p_n         # 随机抽稀
关掉的阵元发 0x10
```

**效果**：

- 打破 10 mm 周期的周期性 → 栅瓣不再相干叠加，变成弥散旁瓣底
- 50% 抽稀典型代价：增益约 −3 dB，主瓣宽约 ×√2
- 栅瓣峰值通常降 10 ~ 20 dB，具体看抽稀率和优化

**优点**：纯主机侧，帧格式不变，最容易先做。

#### 1.2.2 随机相位抖动

每个阵元加 ±1~2 档随机相位：

```text
φ_n' = φ_n + U(-Δ, +Δ)
再量化到 16 档
```

破坏栅瓣的相干条件，把栅瓣能量摊成弥散底。主瓣略降，实现成本极低，适合做基线对比。

#### 1.2.3 相位-only 优化（Phase-Only Optimization）

变量是 256 个阵元的 16 档相位。目标函数可以是：

```text
min  max_{u ∉ 主瓣} |AF(u)| / |AF(u0)|      # 压峰值旁瓣
或   min  ∫_{旁瓣区} |AF(u)|² dΩ             # 压总旁瓣能量
约束 |AF(u0)| = 1，|AF(u_grating)| ≤ ε       # 主瓣增益 + 栅瓣零陷
```

可用方法：

| 方法 | 特点 |
|---|---|
| 坐标下降 | 逐个阵元试 16 档，保留让代价下降的；扫几轮。实现最简单 |
| 模拟退火 | 适合跳出局部最优，速度慢一些 |
| 遗传算法 | 全局搜索，计算量大 |
| 交替投影 / Gerchberg-Saxton | 适合带零陷约束的相位恢复 |

典型收益：峰值旁瓣 −5 ~ −15 dB，特定方向零深 −20 ~ −30 dB。

`demo/array_factor.py` 已有 `compute_array_factor_pattern()` 和 `evaluate_peak_sidelobe()`，可以直接拿来当代价函数。

#### 1.2.4 零陷控制（Null Steering）

在栅瓣方向（正前方 ±59°，转向后位置会移动）加约束，让优化器把该方向压到零。256 个自由度足够；16 档量化会限制零深，通常到 −20 ~ −30 dB 就到头。

#### 1.2.5 相位校准

实际旁瓣很大一部分来自相位/幅度误差：换能器个体差异、走线延迟、驱动板不对称。

- 当前 `Distribute.vhd` 的 `PHASE_CORRECTION` 表只有 0 或 8（0° 或 180° 极性校正）
- 可扩展成 0..15 的逐通道相位校正（改常数表，重建一次）
- 或主机端预补偿：测量每个通道的相位误差，算相位时先减掉再量化，**不用改 FPGA**

典型收益：主瓣增益 +1 ~ 3 dB，旁瓣降低几 dB。测量方法：近场扫描、逐个阵元激励、或麦克风阵列测远场方向图。

#### 1.2.6 子阵 / 非均匀选择

用 8×8 子阵可以加宽主瓣、降低栅瓣的相对影响，但这是牺牲指向性换可用性，不是提升。更合理的是"非均匀子阵 + 优化"，把有效孔径做成低旁瓣稀疏阵。

#### 1.2.7 时间平均 / 多帧抖动

在多帧之间切换不同相位图案，让栅瓣在时间上平均掉。当前只有约 15 帧/秒，效果有限；UART 提速到 256k/512k 后可以做。

#### 1.2.8 注意：模型是各向同性的

`array_factor.py` 假设各向同性阵元、理想相位档。实际换能器有指向性、存在互耦，栅瓣会比模型低一些。**优化前应尽量用实测方向图或实测阵元方向图。**

### 1.3 FPGA 算法 / 固件

#### 1.3.1 逐通道幅度（duty-cycle）—— 最值钱的升级

当前 `PhaseLine.vhd` 的脉冲宽度固定为 9 个 640 kHz 周期（约 56% 占空比），所以只有开/关，没有幅度。

但仓库里已有 `DutyLine.vhd` 和旧 `Control.vhd` 的 duty 控制雏形，说明硬件架构原本支持可变脉宽，只是当前 `AllChannels` 没接。

**做法**：

- `PhaseLine` 加 `duty` 输入，把脉冲宽度设为 `duty` 个周期
- 协议 payload 低 4 位放相位、高 4 位放幅度（或另开一帧）
- `Distribute` 拆分后分别送相位和 duty
- 就能做真正的 Hann / Hamming / Chebyshev 幅度加权

**两个坑**：

1. **脉冲中心要固定**。如果脉冲从相位匹配点开始、只改宽度，脉宽变化会移动相位中心（9→4 周期会偏约 56°）。必须做"居中脉冲"或标定补偿。
2. **基波幅度 ∝ sin(πD)**，在 50% 占空比最大；当前 56% 已接近最大，只能往下调。驱动板和换能器对可变脉宽的响应要实测。

#### 1.3.2 6-bit 相位

`PhaseLine` 端口本来就是 6 位，但 `Distribute` 用 `and 0x0F` 砍到 4 位。提高到 64 档（390 ns/档）能降低量化误差、提高零陷深度。

但这不是改一行 mask 就行：当前相位计数器是 5 位、1.5625 µs 步进；64 档需要 2.56 MHz 的 6 位相位计数器，要动 `Counter` / `AllChannels` / `PhaseLine`，属于中等重构。

#### 1.3.3 逐通道校准表

把 `PHASE_CORRECTION` 从 0/8 扩展到 0..15，或做 6-bit 校准；配合 duty 幅度还能做幅度校准。属于"测量一次、长期受益"的改动。

#### 1.3.4 更快帧率

256k/512k 后，帧率从 15 帧/秒提到 200+ 帧/秒，可以做动态零陷、快速波束扫描、时间平均。

#### 1.3.5 逐通道幅度 + 相位

如果要做多波束、区域控制、不同方向不同音频，需要逐通道幅度+相位。当前硬件和协议都还不够，属于更远的阶段。

## 2. 做流播放

### 2.1 MVP 是什么

**一句话**：主机实时把任意单声道音频流给 FPGA，FPGA 用 FIFO + sigma-delta 门控 40 kHz 载波，现有波束转向保持不变。

MVP 指标：

| 项目 | 目标 |
|---|---|
| 采样率 | 8 kHz（先跑通），再上 16 kHz |
| 位深 | 8-bit 无符号 |
| 声道 | 单声道 |
| 链路 | 256 kbaud（5.12 MHz / 20），约 25.6 kB/s |
| 缓冲 | 1 kB FIFO（8 kHz 下约 128 ms） |
| 调制 | 一阶 sigma-delta @ 5.12 MHz |
| 波束 | 现有相位帧，不变 |
| 延迟 | 约 100 ~ 300 ms |
| 音质 | 窄带、电话级；语音可懂，音乐一般 |
| 新硬件 | 不需要（只需确认 USB 串口芯片支持 256k） |

**这就是不改硬件的天花板。**

---

### 2.2 需要做哪些东西

#### (1) UART 提速

| 项目 | 现在 | MVP |
|---|---|---|
| `g_CLKS_PER_BIT` | 133 | 20（256k）或 10（512k） |
| 主机波特率 | 38400 | 256000 / 512000 |
| `RSSFilter_1` TAPS | 8 | 2 或旁路 |

**RSS filter 是必改项**：8-tap 在 5.12 MHz 下是 1.56 µs；256k 的 bit 才 3.9 µs，占 40%；512k 时几乎一个 bit，会把眼图糊掉。

#### (2) 音频流协议

新增音频包格式（见 2.5），`Distribute` 增加音频包状态机，样本写入 FIFO。

#### (3) FPGA 音频通路

- 1 kB FIFO（1 个 M9K）
- 一阶 sigma-delta 调制器 @ 5.12 MHz
- `stream_en` 选择器：音频模式下 gate 用 sigma-delta，否则保持原 4 种模式
- 欠载处理：FIFO 空时输出静音或保持，避免爆音

#### (4) 资源

- 现在逻辑 90% 已用，只剩约 650 LE
- FIFO 控制 + sigma-delta + 协议解析约 150 ~ 200 LE，理论能塞，但很紧
- 先删 SignalTap；不够就换 EP4CE10/15（引脚兼容），或重构 256 个 `PhaseLine`

#### (5) 主机软件

- WAV：`wave` + `numpy` 重采样到 8/16 kHz，转 8-bit
- 实时麦克风：`sounddevice` 采集，回调写队列
- 按块写串口：8 kHz 下 256 样本 = 32 ms 一块；256k 下写一块约 10 ms
- 独立线程 + 环形缓冲；USB 串口 latency timer 调到 1 ms（FTDI）

#### (6) 测试

1. UART 回环：256k、TAPS=2，连续发已知字节流，确认零错
2. FIFO + sigma-delta：主机发 1 kHz 正弦样本，示波器看占空比
3. 8 kHz WAV：放一段语音，确认能听懂
4. 实时麦克风
5. 16 kHz / 512k
6. 边放边转：音频包之间插相位帧

### 2.4 FIFO 是什么

**FIFO = First-In First-Out，先进先出缓冲队列。**

作用：**解耦生产者和消费者的速率差与抖动。**

```text
UART 写入（256k，约 25.6 kB/s）
        │
        ▼
   ┌─────────┐
   │  FIFO   │  1 kB
   └─────────┘
        │
        ▼
音频读出（8 kHz，8 kB/s）
```

为什么需要：

- 主机（Windows/Python）不是实时的，数据会成批到达、偶尔卡顿
- 8 kHz 采样要求每 125 µs 一个样本；主机做不到这么精确
- FIFO 吸收抖动：1 kB = 1024 样本 = **128 ms** @ 8 kHz，**64 ms** @ 16 kHz

实现要点：

- 写指针：UART 收到字节时写入
- 读指针：8/16 kHz 采样使能时读出
- 标志：空（empty）、满（full）
- 本设计中 UART 和音频逻辑都用 5.12 MHz `CLK_8`，可以做**同步 FIFO**；如果跨时钟域，才需要异步 FIFO + 格雷码指针
- 空：输出静音或保持上一个样本，避免爆音
- 满：丢弃或让主机降速（MVP 用主机按采样率 pace，FIFO 只做抖动缓冲）
- 容量：1 kB 刚好一个 M9K（9,216 bit）

为什么不用单个寄存器：

- 单寄存器没有任何余量，主机一抖动就欠载/溢出
- FIFO 提供几十到上百毫秒的 slack，是流播放能稳定工作的关键

### 2.5 协议是什么

#### 现有相位帧

```text
0xFE | 256 × phase | 0xFD
phase = 0..15   相位档
phase = 0x10    关闭该换能器
```

#### 新增音频包

```text
0xCC | len_hi | len_lo | N × sample | checksum
```

| 字段 | 说明 |
|---|---|
| `0xCC` | 音频包起始（当前未使用，避开 0xC8–0xCB 模式、0xC0/0xC1 板选、0x96/0x97 时钟、0xFE/0xFD 帧） |
| `len_hi/len_lo` | 样本数 N，最大 1024（FIFO 容量） |
| `sample` | 0..255，8-bit 无符号 |
| `checksum` | 1 字节 XOR 或累加和；错误则丢包 |

#### FPGA 状态机

```text
IDLE ──0xCC──► LEN_H ──byte──► LEN_L ──byte──► DATA (N bytes) ──► CHECK ──► IDLE
IDLE ──0xFE──► 原相位帧逻辑
```

- 在 DATA 状态，字节一律当样本，不解析命令
- 长度前缀保证样本字节即使等于 `0xFE/0xFD/0xC8` 也不会误触发
- 包结束后回到 IDLE，可以接收下一个音频包或相位帧

#### 为什么用长度前缀，而不是"裸流 + 转义"

- 样本值覆盖 0..255，任何命令字节都可能出现在样本里
- 长度前缀最简单，不需要转义，也不会破坏相位帧
- 代价是每包 4 字节开销；256 样本一包时约 1.6%，可忽略

#### 相位帧和音频包怎么共存

主机按需插入：

```text
音频包（32 ms） × 5 → 相位帧（258 B，约 10 ms）→ 音频包 × 5 → ...
```

- 8 kHz、256 样本/包：32 ms 一包
- 每 5 包插 1 个相位帧：波束更新约 6 Hz，足够慢速转向
- 带宽：音频约 31%，相位帧约 6%，总共约 37%（256k 下）

注意：**相位帧不能插在音频包内部**，必须在包与包之间。

### 2.6 带宽与资源账

#### 带宽

8N1 每字节 10 bit：

| 波特率 | 有效字节率 | 8 kHz 8-bit | 16 kHz 8-bit | 40 kHz 8-bit |
|---|---|---|---|---|
| 38400 | 3.84 kB/s | 不够 | 不够 | 不够 |
| 256k | 25.6 kB/s | 31% | 62.5% | 不够 |
| 512k | 51.2 kB/s | 16% | 31% | 78% |
| 640k | 64 kB/s | 12.5% | 25% | 62.5% |

建议：**先 256k + 8 kHz**，稳定后再 512k + 16 kHz。

#### 资源

| 资源 | 现在 | 音频 MVP 预估 |
|---|---|---|
| 逻辑 | 5,621 / 6,272（90%） | +150 ~ 200 LE |
| M9K | 1 / 30 | +1（FIFO） |
| 乘法器 | 0 / 30 | 0（sigma-delta 只用加法器） |

风险：90% 已经很满，综合/布线可能收不住。先删 SignalTap，再考虑 EP4CE10/15。

---

### 2.7 风险与未知数

| 风险 | 影响 | 应对 |
|---|---|---|
| 90% 逻辑放不下 | 综合失败/时序差 | 删 SignalTap、优化 PhaseLine、换 EP4CE10/15 |
| USB 串口芯片不支持 256k/512k | 无法提速 | 换 FTDI 模块 |
| RSS filter 糊眼图 | UART 收错 | TAPS 降到 2 或旁路 |
| 换能器带宽窄 | 声音闷、失真 | 先测带宽；接受或换换能器 |
| 栅瓣 | 波束外也能听到 | 抽稀/优化；根治换阵列 |
| 主机抖动/欠载 | 爆音、卡顿 | FIFO + 块写 + 独立线程；或加 MCU |
| 驱动板 5.12 MHz 门控 | 输出异常 | 示波器验证；必要时降门控速率 |
| 功放/换能器温升 | 长时间流播放过热 | 限功率、加散热、间歇测试 |

## 3. 结论与下一步

### 指向性

- **不改 FPGA**：抽稀、抖动、相位优化、零陷、校准都能做，能明显压栅瓣/旁瓣；但幅度只有二值，效果有上限
- **最值钱的固件改动**：逐通道 duty 幅度加权（`DutyLine.vhd` 已有雏形），把"二值抽稀"升级成"真正幅度加权"
- **主瓣宽度**：3° 已是孔径物理极限，算法不能显著变窄

### 流播放

- **MVP**：256k UART + 8 kHz/8-bit + 1 kB FIFO + sigma-delta + 现有波束
- **不需要新硬件**，但要确认 USB 串口芯片和 RSS filter
- **上限**：8–16 kHz、单声道、单波束、窄带音质；不是 hi-fi
- **高保真**：需要宽频换能器、≤ λ/2 间距、逐通道幅度，属于硬件 redesign

### 建议的下一步

1. 先做 **UART 回环**（256k、TAPS=2），这是所有流播放工作的前提
2. 同时测 **换能器带宽 + 基线方向图**，决定指向性优化的目标
3. 写 `demo/beam_optimize.py`：抽稀 / 抖动 / 坐标下降 / 零陷，复用 `array_factor.py`
4. MVP 跑通后再做 duty 幅度固件和 16 kHz
